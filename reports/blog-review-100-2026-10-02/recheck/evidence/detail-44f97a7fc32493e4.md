# 三副本救不了自动恢复的误判：从生产库归零到靠 galera.cache 拼回一百五十个账号
# 0. 先说结果
数据丢了，又拼回来了。
大约一百六十个账号，最后恢复出一百五十个能登录的。靠的是一份八月上旬的旧虚拟机备份，以及 Galera 环缓冲里还没被覆盖的八千多条写入集。
不是完整恢复，是能捞的尽量捞回来了。有些数据和中间的变更，可能永远回不来。
这不是预案的成功，是侥幸的极限。
# 1. 事故是怎么开始的
公司网络不稳定，etcd 一直在超时、恢复、再超时。
K8s 控制平面依赖 etcd。一旦抖动，节点健康检查就会异常，控制平面开始驱逐 Pod、重新调度。MariaDB Galera 这种有状态服务在这种环境下特别脆弱：
  * Pod 被驱逐后，新 Pod 调度到别的节点，PVC 跟着走。
  * 旧节点上的 MariaDB 可能还没完全退出，新 Pod 已经在新节点上起来了。
  * 集群状态不一致，节点互相认为对方落后，出现脑裂风险。
  * 反复几次之后，InnoDB 数据文件开始损坏。


这套库是跑在 K8s 上的三节点 MariaDB Galera，由 mariadb-operator 管理，给账号服务用，体量不大。
问题累积到某一个节点彻底起不来。
# 2. 我做了个错误的决定
recovery 容器里的日志是这样的：

```
2026-09-03 [Note] InnoDB: Header page consists of zero bytes
in datafile: ./ibdata1, Space ID: 0, Flags: 0
2026-09-03 [ERROR] InnoDB: The data file './ibdata1' has the
wrong space ID. It should be 0, but 0 was found
2026-09-03 [ERROR] InnoDB: Plugin initialization aborted
with error Data structure corruption
2026-09-03 [ERROR] Unknown/unsupported storage engine: InnoDB
2026-09-03 [ERROR] Aborting

```

`ibdata1` 还在，但页头全是零，MariaDB 不认。
当时的判断是：这台坏了，另外两台是好的。以前也遇到过类似情况，删掉 PVC，让 operator 从另外两台 SST 同步过来，过一会儿就好了。那次确实奏效过。
于是我又删了 PVC。
# 3. 自动恢复变成了放大器
mariadb-operator 默认开着集群自动恢复。逻辑大致是：
> 集群不健康时，检查各节点状态，选一个 donor 做 bootstrap，其余作为 joiner 加入。
听起来没问题。前提是：每个节点上的数据，都还是「集群真实该有的那份」。
删掉 PVC 之后发生的是：
  * 新 Pod 起来，datadir 是空的。
  * MariaDB 在空盘上初始化一套全新的 InnoDB，生成新的集群 `uuid` 和初始 `seqno`。
  * 当时集群本身就因 etcd 抖动而不稳定，其他节点可能在重启、网络不通，或处于半在线。
  * 自动恢复扫描可用节点时，这台空节点恰好响应最快、状态最「干净」。
  * 问题就出在这里：空节点初始化完成并注册自己的那一刻，落进了扫描窗口。operator 把它当成当前集群的真实状态，选它做 donor，让另外两台有数据的节点当 joiner。
  * Galera 执行 SST：donor 把完整数据目录发给 joiner。只是这次 donor 自己是空的。另外两台有数据的盘，就这样被同步成空库。


空节点本该被当成「新加入的空白成员」，只能跟，不能当源。但不稳定加上竞态，它抢先被识别成「唯一健康的节点」。自动恢复不是故意选了空盘——是空盘在错误的时机出现，而自动恢复判断不了「这个健康的节点是不是太新了」。
事故发生的那一刻，另外两台的数据其实还在。是我交出去，让它们去跟空节点同步的。
# 4. 我犯了哪几个错
## 错误一：把「三副本」当成了「备份」
Galera 保证的是三份一样。SST 会让它们继续一样——包括一样地空。
三副本扛的是节点宕机还能读，不是你把错误状态当成最新之后还能反悔。
## 错误二：自动恢复还开着的时候删了盘
以前这个办法能用，是因为碰巧 donor 是有数据的节点。「碰巧好用」不等于这个操作是对的。
至少该先停掉 recovery，手动看每台的 seqno 和盘里到底有没有数据。只让序号最高、且盘里有内容的那台起来。空盘只能跟，不能当源。
## 错误三：动盘之前没有 dump
这不是技术问题，是操作纪律问题。
哪怕删盘前先 `mysqldump` 一份，后面都不至于这么被动。事故发生时另外两台数据还在，本来可以先备份再动手。
## 错误四：生产环境没有定期备份
operator 的 Backup 没开，集群外也没有定时 dump。
旧虚拟机没删干净，成了唯一的底。那不是预案，是侥幸。
# 5. 靠什么拼回来的
翻出来两样东西。
## 旧虚拟机备份
迁到 K8s 之后，那台旧虚拟机还没删。上面还有一份当时正常跑着的实例，数据大约到八月上旬。这是事故前唯一一份像样的全库底。
## galera.cache 环缓冲
每台机器 datadir 里都有 `galera.cache`。它不是备份，是 Galera 为增量同步准备的写入集环缓冲，大小固定 128MB。InnoDB 被 SST 清掉了，但这个文件如果还没被新写入绕满，旧事务的字节还在上面。
这套库八月中旬在 K8s 上重建过一次，所以 cache 里最早也只到那天。
拷出来两份：
  * 原先有数据的那台：cache 大约用了 5MB，解出八千多条写入集，时间从八月中旬重建一直到事故前一天。
  * 另一个空节点：只剩当天凌晨几条建库、建用户的 DDL，是新集群重新立起来的痕迹。


环缓冲没绕满，纯属运气。
# 6. 恢复过程踩的坑
Galera 的写入集带着行镜像，有现成的离线解析工具，效果接近用 `mysqlbinlog` 解 ROW 事件。
文件头写的当前序号很小，那是空集群自己的编号。有用的是后面还没被覆盖的旧数据。
## 坑一：表结构变过
八月中旬那次导入是按表名字母序写的。排在前面的表——包括账号表的整表插入——正好在文件开头，被新集群那十几条序号盖掉了。后面的表还在。
中途还加过几列。解析必须按「当时有几列」来套。一开始拿最终表结构去套早期事件，字段全对歪了。
## 坑二：账号表整表插入没了
整表插入丢了。但只要这个人在重建之后登录过、改过资料，对应事务的 UPDATE 会带上整行，包括密码哈希。
重建之后再也没写过账号表的静默用户，单靠 cache 救不回来。
只靠 cache，大概捞回八十多个完整账号，其中七十多个带着能用的密码哈希。后来还活着的人基本在；当初导入过、之后再也没登录的那批不在。
# 7. 合并策略
  * 旧虚拟机 dump 打底。
  * 同一条账号，用 cache 里更新过的字段覆盖。
  * 备份之后新注册的追加进去。
  * 登录设备、token、操作日志这类流水不要了。
  * 建表语句也不要，空库上重跑迁移再导数据。


合并结果：  
|  项目   |  数量   |  
| --- | --- |  
|  总账号   |  约 160   |  
|  有密码哈希、能登录   |  约 150   |  
|  只存在于旧备份里的静默用户（真正补上的洞）   |  约 50   |  
|  两边都有、用 cache 补了后来变更的   |  若干   |  
|  八月上旬之后新注册的   |  若干   |  
这不是完整的时间点恢复。是「八月上旬的底，加上重建之后还能看见的变更」。中间那几天、而且之后再也没写过账号表的人，可能还是缺的。
对这个体量来说，能把大约一百五十个能登录的账号拼回来，已经是这两样东西叠在一起的上限。
# 8. 以后怎么做
**短期**
  * 逻辑备份放到集群外面，每天定时 dump 到独立存储。
  * 定期做 restore 演练，确认备份真的能用。
  * Galera 的自动恢复可以留，但删 PVC、强制 bootstrap、改 `safe_to_bootstrap` 必须过人手，不能和「Pod 看起来不健康」自动串在一起。


**中期**
  * 排查 etcd 不稳定的根因，从基础设施减少无意义的节点驱逐。
  * 给 MariaDB 加 PodDisruptionBudget 和节点反亲和，减少非必要调度。


**长期**
  * `galera.cache` 仍然不是备份。这次没写满，才救了十几天的数据。下次不会这么巧。
  * 要有真正的 PITR，而不是靠环缓冲捞碎片。


# 9. 最后
Galera 的 SST 没有恶意：你让谁当主，它就把谁的状态扩散出去。
operator 的 recovery 也没有恶意：它选它认为序号最高、状态最干净的那台。
两者叠在「我刚删了一块空盘」上，空库就会变成真相。
三副本真的很能麻痹人。
这次能从 cache 和一台没删除的虚拟机里拼回大部分账号，不代表下次还能。环缓冲会绕满，旧机器也不会永远留着。
网络会恢复，etcd 会稳定，数据不会自己长回来。
备份要自己做。
